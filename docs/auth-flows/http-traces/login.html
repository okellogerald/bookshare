Note — Why the login challenge?
Hydra delegates authentication to the Auth Portal. The login challenge is a one-time token tying this OAuth2 request to whatever authentication the Auth Portal performs. The Auth Portal must later "accept" or "reject" this challenge via Hydra's Admin API to resume the OAuth2 flow.

Note — Boxed auth design
By storing the challenge in a cookie, the Auth Portal decouples the login UI from OAuth2. The /login page doesn't need return_to URL threading or Hydra awareness. When login completes, the Auth Portal reads the challenge cookie to resume the OAuth2 flow.

Understanding the login JSON
"identifier" vs "traits.email"
Login uses "identifier" instead of traits.email. Kratos resolves this to an identity by checking all configured identifier traits. The user types their email but Kratos treats it as an identifier lookup.
group: "default" vs "password"
identifier is shared across all methods. password and method=password are specific to the password method. If social login were configured, additional groups would appear.
Single-step flow
Unlike registration (profile → password), login presents everything at once. No screen=previous navigation.
Note — Simpler than registration
Login is simpler than registration — one step with all fields. BookShare still converts the Kratos nodes into a login model to control field ordering and fail loudly if the shape changes.

Note — The three gates
The Auth Portal's /oauth/login handler is the central decision point. It checks: (1) Session — is the user authenticated? If not → /login. (2) Verification — is email verified? If not → /verification. (3) Profile — is profile complete? If not → /settings. Only when all pass does it accept the Hydra challenge.
