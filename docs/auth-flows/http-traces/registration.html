Note — Why 303 and not 200?
Kratos intentionally does not return the flow details here. The CSRF cookie is set on Kratos' origin (localhost:4433), but the Auth Portal lives on a different origin (localhost:3337). Due to the browser's Same-Origin Policy (SOP), only the origin that set the cookie can read it. By redirecting back to the Auth Portal with just the flow ID, Kratos forces the Auth Portal to fetch the flow in a separate request (Stage 2) where the browser automatically attaches the CSRF cookie — proving the request is coming from the same browser session that initiated the flow. This two-step pattern (create → redirect → fetch) prevents cross-origin actors from reading or hijacking the flow.

Understanding the JSON response

Kratos returns a generic ui.nodes array. Each node is a form element instruction. The Auth Portal interprets these to build the registration form:

"state"
The flow's current phase. "choose_method" means Kratos is waiting for the user to pick an authentication method (profile first, then password).
"ui.action"
The URL the form must POST to. Always points to Kratos, not the Auth Portal.
"group"
Which authentication method a node belongs to. "default" = shared across all methods (identity traits, CSRF). "profile" = the profile collection step. Later, "password" = the credential step.
"name"
The form field name. "traits.*" fields map to the identity schema (e.g. traits.email, traits.name.first). "method" tells Kratos which step is being submitted.
"type"
The HTML input type to render: "hidden", "email", "text", "password", or "submit".
"value"
A pre-filled value. For submit buttons, this is the value sent when clicked (e.g. "profile" tells Kratos "I'm submitting the profile step").
"required"
Whether the field must be filled before submitting. Only traits.email is required at the profile step.
Note — No password field yet
Kratos uses a two-step registration flow. In this first step, only group: "default" (trait fields) and group: "profile" (the profile submit button) are present. The password field (group: "password") only appears after the profile step is successfully submitted. This is by design — Kratos validates identity traits before asking for credentials.

Compare this response with Stage 2's. Same flow ID, but the nodes have been restructured by Kratos:

Note — Flow ID and token change
This is the boundary between registration and verification. Three things change at once:

1. New flow ID. The registration flow ID (4edd5173...8559) is finished. Kratos creates an entirely separate verification flow with its own ID (46d2420a...ca3f). These are different self-service flow types in Kratos — the registration flow is consumed and cannot be reused.

2. CSRF cookie rotated. The cookie value changes from 6LtE33nN... to CLqlnMNJ.... Kratos rotates the CSRF token when transitioning between flows for security — the old token tied to the registration flow is no longer valid.

3. Different route. The redirect points to /verification instead of /register. The Auth Portal's verification route handler (not the registration one) will process this request.
Note — No session created
Kratos' show_verification_ui post-registration hook is configured to redirect to verification instead of creating a session. This is by design — BookShare requires email verification before login. The user's identity exists in Kratos, but they cannot authenticate until verification completes.

Understanding the verification JSON

The verification flow uses group: "code" instead of "profile" or "password". The node structure is different from registration:

"state": "sent_email"
The verification flow is already past initialization — Kratos sent the email when it created this flow in Stage 5. Compare with registration's "choose_method" state.
"active": "code"
The active verification method. Kratos supports multiple verification strategies; BookShare uses the code method (a 6-digit code sent via email).
hidden method=code
A hidden field that tells Kratos which verification method is being used when the form is submitted. Always included automatically.
name: "code"
The text input where the user enters the 6-digit verification code from their email. This is the only visible field.
submit method=code
The submit button. Sends the entered code to Kratos for validation.
submit email=...
A resend action. Clicking this submit button (with name: "email" and the email as its value) asks Kratos to send a new verification code. This is how "Resend code" works.
